编程智能体 (Coding Agents)

学习目标​

  • 区分标准 AI 助手与自主编程智能体
  • 使用 Cursor 或 Claude Code 等工具配置编程智能体环境
  • 使用智能体工作流执行大规模的多文件重构
  • 通过 diff 审查和测试套件验证并审计智能体生成的变更

从 Copilot 到 Agent​

标准的 AI 助手（通常被称为 "Copilots"）主要通过自动补全或聊天界面运行。它们基于“请求-响应”模式工作，通常只关注你当前编辑器标签页中可见的代码。

编程智能体（Coding Agents）代表了向自主化迈进的范式转变。与简单的聊天界面不同，智能体可以读取你的整个文件树、执行终端命令并编辑多个文件以实现目标。这种能力由智能体循环 (Agentic Loop) 驱动：

  1. 感知 (Perceive)：智能体扫描代码库，读取相关文件并理解目录结构。
  2. 规划 (Plan)：AI 制定实现请求变更的逐步策略。
  3. 执行 (Act)：智能体执行操作，例如编写代码、创建新文件或运行构建脚本。
  4. 评估 (Evaluate)：智能体通过运行测试或分析错误日志来检查其工作成果，以确保计划成功。
── 智能体循环 ────────────────────────────────────────────────────
  用户指令
       ↓
  感知 ──→ 读取文件、搜索代码库、理解结构
       ↓
  规划 ──→ 将目标分解为有序子任务
       ↓
  执行 ──→ 编写/编辑文件、运行 shell 命令
       ↓
  评估 ──→ 运行测试、读取错误输出
       ↓
  ┌── 通过？──→ 完成，展示 diff 供审查
  └── 失败？──→ 带着新观察结果回到感知阶段

循环在智能体认为任务完成、或达到配置的最大迭代次数时退出。评估步骤是智能体与简单自动补全的本质区别：真实的反馈（测试失败、编译错误）会作为新上下文重新进入循环。

搭建你的智能体环境​

为了有效地使用智能体，你必须为其提供全局上下文。这通过代码库索引（或嵌入/embedding）来实现，即 AI 为你的整个项目创建一个可搜索的数学表示。如果没有适当的索引，智能体可能会遗漏远端目录中的关键依赖项。

目前有多款基于 CLI 的编程智能体可供选择，它们遵循相同的智能体循环，但工具集成方式各有不同：

工具安装命令启动方式
Claude Codenpm install -g @anthropic-ai/claude-code在项目目录中运行 claude
Aiderpip install aider-chataider
Cursor（IDE）从 cursor.com 下载打开项目文件夹

无论选择哪款工具，第一步都是让它访问你的代码库。CLI 智能体在首次运行时会自动索引项目；IDE 智能体则在后台完成嵌入。

Terminal — Claude Code 示例
# 进入项目目录，启动智能体
cd my-project
claude

执行大规模重构​

在使用智能体时，你应该从“单文件”提示（即将代码片段复制粘贴到聊天窗口）转向“项目级”指令。与其告诉 AI 如何修改一个函数，不如描述架构意图，并让智能体识别所有受影响的文件。

以下示例展示了一个针对复杂重构的高层级指令：

agent_prompt.md
将 UserAuth 服务从已废弃的 JWT 实现迁移到新的 OAuth2 提供商。

1. 更新 `auth_provider.py` 接口以匹配新的方法签名。
2. 找到所有使用旧 `validate_token` 方法的控制器，并将其更新为使用 `verify_oauth_token`。
3. 确保 `/tests/auth` 中的集成测试也同步更新以反映这些变更。
注意

在启动智能体重构之前，请务必确保你处于一个干净的 Git 分支上。智能体可以在几秒钟内修改数十个文件，如果没有版本控制，手动撤销更改将变得极其困难。

人在回路：审查与验证​

“人在回路 (Human-in-the-Loop, HITL)”模式是智能体工作流中最关键的部分。你绝不能将智能体的输出视为最终成品。你的角色从编写代码转变为审计代码。

在智能体完成任务后，使用 Git 工具检查每一次修改，并运行现有的测试套件以捕获任何回归问题。

# 审查智能体修改的所有行
git diff main..feature-refactor

# 查看哪些文件被修改
git diff --name-only main..feature-refactor

# 运行完整的测试套件
npm test

在阅读 diff 时，重点关注三类风险：删除的行（有没有不应该删除的内容被删掉了？）、重命名的标识符（智能体是否重构了不该改动的东西？）、以及新增的外部调用（是否引入了意外的依赖或网络请求？）。

提示

如果智能体陷入循环或在两次尝试后仍无法修复 bug，请提供关于其遗漏的文件或逻辑的具体提示，而不是简单地要求它”再试一次”。

端到端示例：OAuth2 迁移​

以下追踪记录展示了智能体接收到上述 OAuth2 重构指令后，循环内部的实际执行过程。

端到端：智能体执行多文件重构
用户："将 UserAuth 从已废弃的 JWT 迁移到 OAuth2 提供商。"

── 循环迭代 1 ───────────────────────────────────────────────────
感知  搜索代码库中的 "validate_token"，找到：
      auth_provider.py（第 34 行）、users_controller.py（第 12 行）、
      payments_controller.py（第 88 行）、tests/auth/test_login.py（第 5 行）
规划  子任务：
      1. 更新 auth_provider.py 接口
      2. 更新 users_controller.py
      3. 更新 payments_controller.py
      4. 更新 test_login.py
执行  编辑 auth_provider.py——将 validate_token 签名
      替换为 verify_oauth_token(token: str, scopes: list[str]) -> dict
评估  运行：pytest tests/auth/
      结果：3 个失败（控制器仍调用旧方法名）

── 循环迭代 2 ───────────────────────────────────────────────────
感知  读取失败输出——确认 3 个文件仍使用 validate_token
执行  编辑 users_controller.py、payments_controller.py、
      test_login.py——更新所有调用处
评估  运行：pytest tests/auth/
      结果：全部 12 个测试通过 ✓

── 最终结果 ─────────────────────────────────────────────────────
智能体展示 diff：4 个文件变更，18 行新增，9 行删除
开发者审查 git diff，确认变更正确，合并分支。

智能体运行了 2 次迭代——不是因为被告知要这样做，而是测试失败提供了具体反馈，作为新的观察结果重新进入了循环。

常见失败模式​

症状可能原因解决方案
智能体编辑了错误的文件（无关模块）指令过于模糊——未指定文件或方法名在 prompt 中明确指出具体的文件路径和方法签名
智能体在同一个失败测试上无限循环未设置迭代限制；LLM 重复尝试相同方案设置 max_iterations（10–20）；失败 2 次后提供关于具体错误的提示
智能体静默跳过某个文件代码库未被索引/文件被排除在上下文之外重新索引，或在 prompt 中明确指出文件路径
重构通过了测试但破坏了生产行为测试未覆盖被修改的代码路径运行更全面的测试套件，而不仅仅是 auth 测试；先补充缺失的测试覆盖
智能体引入了新的外部依赖prompt 中未添加约束条件在 prompt 末尾加一行约束："不得添加项目中尚未存在的新依赖或导入。"

练习​

创建一个名为 refactor-test 的新 Git 分支。使用编程智能体在你项目中查找特定硬编码字符串的所有实例，并将其替换为在新的 constants.py 文件中定义的常量。智能体完成后，使用 git diff 验证所有实例是否已正确更新，且没有引入任何语法错误。

小结​

  • 编程智能体在感知 → 规划 → 执行 → 评估的循环中运行，测试失败和错误输出会作为新上下文重新进入循环。
  • 代码库索引对于为智能体提供复杂任务所需的全局上下文至关重要。
  • 高层级指令优于单文件提示——描述架构意图，让智能体找到所有受影响的文件。
  • 通过 Git diff 和自动化测试套件进行人工监督是确保代码完整性的必要手段：重点关注删除的行、重命名的标识符和新引入的外部调用。
  • 在 prompt 中添加约束条件（如”不得添加新依赖”）可以显著减少意外变更。
