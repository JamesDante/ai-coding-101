## Learning Objectives

* Define tools using JSON schema for LLM consumption
* Implement the request-response cycle of a function-calling loop
* Execute local shell commands safely via an AI agent
* Feed tool outputs back into the model context to generate final answers

## What is Tool Calling?

When you interact with a Large Language Model (LLM), the model generates text based on patterns in its training data. However, an LLM cannot "reach out" and touch your computer. It cannot check your file system, run a Python script, or query a database directly.

Tool calling (often called function calling) is the mechanism that bridges this gap. In a tool-calling workflow, the model does not execute code itself. Instead, it recognizes when a task requires an external action and outputs a structured request—usually in JSON format—containing the name of the tool to use and the necessary arguments.

The responsibility for execution lies with your application (the client). Your code parses the LLM's request, runs the actual function on your local machine, and then sends the result back to the model. This creates a loop where the AI can observe the results of its actions and decide on the next step.

## Defining Tool Schemas

To enable tool calling, you must provide the LLM with a blueprint of available tools. We use JSON Schema to describe these tools. This schema tells the model what the tool does and exactly what parameters it expects.

Clear descriptions are the most important part of this definition. The LLM uses the `description` field to decide whether a tool is appropriate for the current user prompt. If your description is vague, the model may fail to trigger the tool or provide incorrectly formatted arguments.

```json title="tool_definition.json"
{
  "name": "run_script",
  "description": "Executes a local shell command or Python script and returns the output.",
  "input_schema": {
    "type": "object",
    "properties": {
      "command": {
        "type": "string",
        "description": "The full shell command to execute, e.g., 'ls -la' or 'python3 script.py'."
      },
      "timeout": {
        "type": "integer",
        "description": "Maximum time in seconds to allow the command to run.",
        "default": 30
      }
    },
    "required": ["command"]
  }
}
```

:::tip
When writing tool descriptions, use imperative language (e.g., 'Use this tool to fetch...') and be explicit about the expected format of the input parameters.
:::

## Implementing the Tool Loop

The "loop" is the engine of an AI agent. It is a continuous cycle that manages the conversation history and handles the transition between user input, model reasoning, and tool execution.

The process follows these steps:
1. Send the user prompt and the tool definitions to the LLM.
2. Check the model's response. If the `stop_reason` indicates `tool_use`, extract the tool name and arguments.
3. Execute the corresponding local function using those arguments.
4. Append both the model's tool request and your function's output to the conversation history.
5. Send the updated history back to the LLM.

```python title="agent_loop.py"
import json

def run_agent_loop(client, model, messages, tools):
    while True:
        # 1. Send request to the LLM
        response = client.messages.create(
            model=model,
            tools=tools,
            messages=messages
        )
        
        # Add the assistant's response to history
        messages.append(response.content[0])

        # 2. Check if the model wants to use a tool
        if not response.stop_reason == "tool_use":
            break

        # 3. Process tool requests
        for content in response.content:
            if content.type == "tool_use":
                tool_id = content.id
                tool_name = content.name
                arguments = json.loads(content.input)

                print(f"[*] Executing tool: {tool_name} with {arguments}")
                
                # Execute the actual local logic
                result = execute_local_tool(tool_name, arguments)

                # 4. Feed the result back into the history
                messages.append({
                    "role": "user",
                    "content": [
                        {
                            "type": "tool_result",
                            "tool_use_id": tool_id,
            "content": result
                        }
                    ]
                })

    return messages[-1].content # Return the final text response
```

## Building a Local Script Executor

A practical implementation of a tool often involves interacting with the operating system. We can use Python's `subprocess` module to capture the output of shell commands. By capturing both `stdout` (standard output) and `stderr` (error output), we provide the LLM with full visibility into whether the command succeeded or failed.

```python title="executor.py"
import subprocess

def execute_local_tool(name, arguments):
    if name == "run_script":
        command = arguments.get("command")
        try:
            # Run the command and capture output
            process = subprocess.run(
                command,
                shell=True,
                capture_output=True,
                text=True,
                timeout=arguments.get("timeout", 30)
            )
            
            # Combine stdout and stderr so the LLM sees everything
            output = process.stdout
            if process.stderr:
                output += f"\nErrors:\n{process.stderr}"
            
            return output if output else "Command executed successfully (no output)."
            
        except subprocess.TimeoutExpired:
            return "Error: The command timed out."
        except Exception as e:
            return f"Error executing command: {str(e)}"
    
    return "Error: Tool not found."
```

:::warning
Never allow an LLM to execute arbitrary shell commands on a production system without strict sandboxing or human-in-the-loop approval, as this creates a critical security vulnerability.
:::

## Error Handling and Self-Correction

One of the most powerful features of tool calling is "self-correction." Because the error messages from your local environment are fed back into the model's context, the LLM can see exactly why a command failed.

If a Python script crashes with a `Traceback`, the LLM receives that traceback as a `tool_result`. The model can then analyze the error, realize it passed an incorrect file path or a malformed argument, and attempt to call the tool again with corrected parameters.

```python title="error_handling_demo.py"
# Example of how the loop handles a failure
messages = [
    {"role": "user", "content": "Run a script to check if 'config.json' exists."}
]

# If the tool returns: "Error: FileNotFoundError: [Errno 2] No such file or directory: 'config.json'"
# The LLM sees this in the history and can respond with:
# "I attempted to check for config.json but it wasn't found. Let me try listing the current directory instead."
```

By treating errors as just another form of input, you transform a static script into an adaptive agent capable of navigating complex, unpredictable environments.

## Summary

* Tool calling allows an LLM to request actions that the client executes locally.
* JSON Schema is used to define the interface, name, and parameters of a tool.
* An execution loop is required to manage the back-and-forth between the model and your local functions.
* Capturing `stderr` is essential for enabling the LLM to perform self-correction after a failed command.
